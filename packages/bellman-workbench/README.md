# Bellman Workbench

For setup and first use, see [Install Bellman Workbench](../../docs/overview/00-install.md).

A page on your own machine that reads a stage file as you type it and draws, beside the text, the operators the equations denote. Nothing in the drawing is drawn by hand: every box came from a line of the file, a click on a box takes you to that line and prints its mathematics, and a line the language refuses is marked at its line and column, its sentence in the package's own words standing in the page's one list of refusals, while the last good drawing stays, dimmed. The Workbench solves nothing. Outside the model folder it stores the views of a trellis's stages and the bound trellis in the user's cache folder, and the local Matsya session identifier described below; the browser keeps the sizes and folds of the window's regions and the choice `high contrast`. Git is the only history of model files.

Install it beside `bellman` with its extra `explore`, which provides the graph exporter. From a checkout: `venv/bin/python -m pip install -e "packages/bellman[explore]" -e packages/bellman-workbench`. From the two built wheels: `pip install "bellman-0.1.7-py3-none-any.whl[explore]" bellman_workbench-0.1.0-py3-none-any.whl`. The page's files, fonts and Solara's interface files are installed with the Workbench. For a machine without network access, first gather both wheels and all dependency wheels on a connected machine with `pip download --dest wheels "bellman-0.1.7-py3-none-any.whl[explore]" bellman_workbench-0.1.0-py3-none-any.whl`, then install with `pip install --no-index --find-links wheels "wheels/bellman-0.1.7-py3-none-any.whl[explore]" wheels/bellman_workbench-0.1.0-py3-none-any.whl` on a compatible Python and platform. Start it on the portfolio model, `bellman-workbench applications/portfolio-choice`, which runs Solara's server and opens the browser at `http://localhost:8765/` (`--port`, `--host` and `--no-open` change that). Click `cons.bl` under `declaration/stages/cons/` in the folder at the left. Lesson 01, `tutorials/getting-started/01-the-stage.ipynb`, reads the same file in a notebook.

## Matsya

At the right of the window stands Matsya's column, its name beside a periwinkle Υ, in which a question typed in words is answered by Matsya, the project's retrieval service over its documents, theory and examples, with the passages the answer rests on listed under it, each named by the path the service gives for it. The column opens unfolded; the button `Matsya` at its head folds it, the column then taking no width, and the button `Matsya` on the rail folds and opens it; the browser keeps the fold with the regions' sizes; its questions and answers stay for the page's life; opening another folder, as `new trellis` does, empties them. A question is sent with the button `ask` or the Enter key, in a conversation of the service named by the first twelve characters of the SHA-256 digest of the folder's path, and the page stays in use while the service answers; the client's own defaults choose the language model. The service keeps that conversation: it reads the conversation's earlier questions and answers with each new question, and stores them as session records on the server. The field is a text area: Enter sends the question and Shift+Enter begins a new line, pasted text keeps its line breaks, the field grows with its text to eight lines and then scrolls, and the top edge of the box that holds the field is a handle that sets the field's height, which a double click on it releases; Escape returns the focus to the conversation. The column runs the Bellman client command `bellman-matsya`, which the Workbench finds beside the Python interpreter that runs it, in its own environment, or else on the Workbench server's command search path. From a Bellman checkout, install it into the Python environment that runs the Workbench with `venv/bin/python -m pip install -e packages/bellman-matsya-client` and run `venv/bin/bellman-matsya configure` on macOS or Linux, or use the corresponding executables in `venv\Scripts\` on Windows. Enter the private Matsya token and Bellman service address supplied by the administrator; do not put the token in a model file or chat. The client stores them in `~/.config/bellman-matsya/config.toml`. The earlier HARK ask-your-project Matsya client and its token do not configure this Bellman client. If the command is in neither place, set `BELLMAN_WORKBENCH_MATSYA` to its full path before starting the Workbench. Set the variable to `off` to remove the column and run no client. Without the command, the column reads `Bellman Matsya's client bellman-matsya was not found`; when the service does not answer, it reads `Bellman Matsya did not answer`.

The column sends the question and the digest used as the conversation name, but no model file contents unless you paste them into a question. It changes nothing in the model folder. The Workbench keeps no local question log or token of its own; it writes the service's session identifier for the folder under `~/.config/bellman-matsya/workbench-sessions/`.

In a folder connected to Matsya, choose **Build declaration** in the composer, write the request and press **Prepare build**. A folder can start with a description in `economics.md` or in the request. Review the output level, session entries, outgoing text and any selected declaration files before pressing **Build declaration** on the review. If the session changes during preparation, prepare the build again. Workbench restores jobs started in chat and offers to resume a reviewed submission when its acknowledgement was lost.

A job's comparison and unanswered assumptions appear separately from local construction and numerical checks. When you download and inspect a declaration, Workbench lists any value functions the terminal period still requires. Use **Adopt first declaration** for a folder with an empty declaration, or review the destinations under **Replace model files…** for a build based on the current project.

## Creating a model and keeping it in git

`new trellis` writes a model folder beside the open one, in the parent folder its form asks for, which holds the folder that holds the open model folder until another is typed, a full path or one from `~`, and which is never a model folder nor a folder inside one; the folder is written from the templates of the application corpus: the four stage files of `applications/portfolio-choice/` with the calibration, settings and methods files `applications/cons-port/` binds them with, and the four stage files of `applications/pension-retirement/`. A template whose stage file the package refuses keeps its place in the form's list with its rule, the package's sentence in its hover, and the others are offered; with no template chosen, the folder is written with no stage, for `new stage` to fill. The folder holds, under `declaration/`, each stage in a folder of its own, `stages/<key>/<key>.bl` with the additions its template brings, `methods.bl`, the calibration and settings files under `calibration/` and `settings/`, and `period.yml`, `trellis.yml` and `spec.yml` with the calibration and the settings of each stage a slot and its methods list naming the additions; at its top it holds `answers.yml`, a `.gitignore` and a three-line `README.md`; outside a repository it is made one, with the push destination typed in the form. The page opens the new folder with its recipe in the editor and offers the first commit, which is made only when `commit` is pressed. Every form is one panel, closed by `×`, `cancel` or Escape, its button that writes also pressed by Command+Enter on macOS or Ctrl+Enter elsewhere, a refusal standing on one line under the field it concerns. `add stage` and `add period` copy one more stage, or write one more period, into such a folder, editing the YAML files as text so that their comments stay; Problems lists each refused binding, unjoined internal arrival field and entry `answers.yml` marks to check, with its source controls; a slot of the recipe, a place for values supplied by the keyword of `load_recipe` of the same name, is no problem, and the line `slots` under the recipe's blocks lists those keywords. A slot whose file the folder does not hold offers, in its binding's lists under the tree, `new file` beside `replace`, which writes that file empty under `declaration/`, `calibration/<key>.yml`, `settings/<key>.yml` or the empty addition `stages/<key>/methods.bl`, writes its name in the slot's place and opens it. The `new variant` form names the selected recipe and gives the variant its own recipe, trellis file and period files. Choose **Share binding files** when both recipes should use the same calibration, numerical settings and method assignments. **Copy binding files for this variant** is selected by default and gives the variant independent copies. The copies keep the order of each assignment and use one copy for each file shared by several stages. This includes files listed under `registry`, which may supply period ages, and the parents from which binding files inherit values. Both choices share the stage declarations; the copy writes an addition as `methods.<variant>.bl` beside its stage file. The form opens the new recipe and shows its trellis. Git's line holds `commit` and `push` where a repository holds the folder, and `export view` while a stage or a trellis is shown. `commit` commits the folder's files you name, `git commit --only`, leaving other staged work as it is; `push` uses the credentials git already holds and shows git's own sentence, on git's line where the push succeeded, and in the Problems list, with `push` marked in orange, where it failed; `export view` writes the shown view under `model-explorer/` with a record of its inputs and the commit.

## Connections between stages

A field name belongs to its stage: `cons.a` and `port.a` are different fields. The Workbench draws the package's selected connections and shows their compatibility in Details. Equal names can select a connection when the package establishes a unique compatible match. Otherwise the stage remains visible with its unconnected fields. An unresolved authored endpoint remains in the source and its package diagnostic appears in Problems.

Move either end of an inferred or authored arrow to write its replacement as a compact mapping, such as `{cons.a: port.b}`. A stage prefix is included only where the bare field name is ambiguous. The complete proposed edit is checked before it enters the buffer; declared sets, shared period parameters and backward value requirements are checked by Bellman. Moving several fields checks their final mapping together, so `{a: b, b: a}` is simultaneous. An incomplete route can be built a field at a time and remains marked incomplete until the package certifies it.

A connector in a shared period file changes every period that reads that entry; the edit names those periods and checks them all. To change one occurrence, first give it its own connector source. Dropping an arrow on its current endpoints changes nothing. Undo and redo restore the source and the selected connections. An edit that depends on an unavailable calibration value is refused; independent symbolic comparisons remain available while the calibration diagnostic stays visible. Retained older values cannot authorize an edit after their replacement was refused. An event from an older reading must be repeated on the current graph.

## What it does not do

It reads no model file with a parser of its own; the only parser of the language is the package's. It runs no numerical method and solves nothing. It stores no layout, no size of a region and no place of the page's history in the model folder, writes connector edits from explicit graph gestures into the source buffer, with undo, and keeps the other diagrams read-only. It carries no assistant that acts on the model: its one window onto a service, Matsya, sends the question typed in it, with a digest of the folder's path as the name of the conversation, and nothing else. It commits nothing on its own, resolves no conflict and stores no token in its own files, and sends nothing to any service but that question and that digest. It reformats no file. It adds no terminology: the words on screen are the documentation's.

A file a trellis reads outside the folder, as a stage file of `applications/portfolio-choice/` that cons-port's trellis files read, opens in the editor under its path relative to the folder, `../portfolio-choice/declaration/stages/cons/cons.bl`, and the tree and git's letters cover the folder alone. One command serves one folder. A tab that opened the folder `new trellis` wrote returns to the command's folder when the page is reloaded; `bellman-workbench <new folder>` opens the new folder itself. The templates are read from the corpus of the checkout the Workbench is installed from editable. The stages of the library, listed under `library` after the templates and copied into the model folder as a template is, are read from the folders the environment variable `BELLMAN_STAGE_LIBRARY` names, several joined by the path separator, or from `~/.bellman/library/` where the variable is not set and that folder exists, each folder there that holds one stage file being one stage, and nothing in the library is written. The page tests need headless Chromium: Playwright's own, or the executable the environment variable `BELLMAN_WORKBENCH_CHROMIUM` names. Every face the page draws is served from the package: Archivo for labels and prose, where the design names PP Monument, whose license for distribution is not settled; IBM Plex Mono for the source, the tabs, the running heads and the tools; and STIX Two Math for the letters and symbols the other two lack, Υ and the graph's mathematical italic among them.

## How it is built

The package is a distribution of its own, `packages/bellman-workbench/`: `bellman_workbench/model.py` is the backend, which imports no Solara and is what the tests and a later language server read, and beside it, importing no Solara either, `recipe.py` reads the sources of the folder's trellis, binds a buffer as the occurrence the head names, answers the recipe's rows, one per stage, and the rows of the BellmanType panel's tabs `Parameters`, `Settings` and `Methods`, and writes the values and the methods typed or chosen there, `trellis.py` reads, elaborates, binds and draws the trellis, restricted as the view's bar asks, `creation.py` writes a new model folder from templates of the corpus, edits it with `add stage` and `add period`, writes a variant of its recipe with `new variant`, each YAML file edited as text by the package's writers of `bellman.trellis`, and lists the entries `answers.yml` marks to check in Problems, and `navigation.py` answers the places of the page, its history of steps back and forward and the parts of the breadcrumb; `app.py` is the Solara page; `editor.vue`, `graph.vue`, `classification.vue`, `values.vue`, `copy.vue`, `goto.vue`, `restriction.vue`, `status.vue` and `window.vue` are the Vue components of the editor, the view, the BellmanType panel's tab `Fields`, its tabs `Parameters`, `Settings` and `Methods`, the button that copies a card, Goto Anything, the select of the trellis view's restriction, the measure that places the parts of the trellis's status line, and the window's column widths, folds, handles, keys and high-contrast setting; `brand.css` holds every color and size of the page as a custom property, which the editor's theme reads; `command.py` is the console command; `matsya_client.py` holds `ask`, the one function by which the page asks Matsya a question, and `run`, by which `matsya_work.py` runs the client's other commands; `matsya_work.py` prepares the inputs of a job, records each request before its answer is awaited, recovers those records, checks that a job belongs to the selected session on the effective service and downloads a job's products under `bellman-matsya-output/`, its docstring defining the files it writes (specification 0.6, unit G2); `returned.py` opens such a saved copy as a model of its own, plans and records the adoption of its reviewed files with the originals kept for recovery, restores or completes a stopped adoption, and imports a copy's changed calibration, settings and methods files as a variant, its docstring defining the adoption's record (specification 0.6, unit G3); and `matsya_window.py` holds the Matsya window. The files the page loads are under `bellman_workbench/public/`, served at `/static/assets/`, none edited by hand: `bellman_workbench/public/codemirror/bellman-workbench.js`, the editor, built from `js/codemirror/` by Rollup with `js/codemirror/build.sh` (the Node version and the digests of the build are recorded in `js/codemirror/README.md`, with `bellman_workbench/public/codemirror/LICENSES.txt`, the notices of the packages it is built from; its colors are the custom properties of `brand.css`: keywords and perch tags periwinkle, role tags and sets mint, numbers light orange, function names italic, a block's id in its header bold, and the header's brackets and a statement's annotation ice-3); `bellman_workbench/public/flow/`, the React Flow graph bundle built from `js/flow/` with `js/flow/build.sh`, beside ELK, the base stylesheet and STIX Two Math with its notice, with build commands and digests recorded in `js/flow/README.md`; `bellman_workbench/public/fonts/`, Archivo and IBM Plex Mono with their licenses, copied by `js/fonts/build.sh`, whose record is `js/fonts/README.md`; `bellman_workbench/public/notebook/template.ipynb`, the cells `notebook` writes; and `bellman_workbench/public/brand/`, the brand's mark and favicon, copied from `docs/_assets/brand/`, the favicon served where Solara's page links it through the asset locations `app.py` adds.

`graph.vue` loads the graph assets and mounts the graph inside the page. Solara's own interface files and their notices are package data under `bellman_workbench/solara-cdn/`, fetched by `js/solara-cdn/fetch.py`. The command serves them locally through `SOLARA_ASSETS_PROXY_CACHE_DIR`.

## Desktop file requests

The desktop application uses the same page and server as the browser. A URL
such as `/?file=declaration/stages/cons/cons.bl&line=24` opens that file and
selects the block containing the line after elaboration. An optional `box`
selects a named graph box. File paths must be relative to the model folder;
links cannot open files outside it. Opening a link preserves unsaved buffers.

To offer **open in editor** beside a selected box's source lines, set
`BELLMAN_WORKBENCH_EDITOR` to a JSON list of command arguments before starting
the server, for example `'["code", "--goto"]'` or `'["cursor", "--goto"]'`.
The Workbench adds the absolute file path and line as one argument. The editor
opens the saved file; unsaved Workbench text remains in the Workbench. Source
paths already read from a recipe can refer to files outside the model folder.

On Windows the editor command must name the native executable, such as
`Code.exe` or `Cursor.exe`; `.cmd` and `.bat` commands are refused.
