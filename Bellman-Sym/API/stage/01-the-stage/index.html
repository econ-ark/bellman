    The stage¶

    Summary

    elaborate_stage turns one stage file, a .bl file, into one Python object, the stage. This page states how a stage is made, the seven attributes it holds and the questions it answers about itself: its printed view, its contents, its fields, its conditions, its diagnostics and its encoding. Every listing is printed by the package from the consumption stage applications/portfolio-choice/declaration/stages/cons/cons.bl.

    Relationship with other documents

    Builds on — Stage tutorial: the stage file line by line. Used by — The initial diagrams, The builders graphs and the pages after them: the pieces reached from the stage. See also — API: the functions that make a stage in §2.1 and every path of the stage in §2.4; The factory API: the functions that load, elaborate and bind a trellis of stages.

    Each python block on this page runs after the blocks above it, in one session started at the repository's root, and the text below a block is what that block prints.

    1 Making a stage¶

    A stage file holds declarations and blocks. Each block lists the fields it reads and the fields it writes, and it denotes an operator: on value functions when it is read backward, on finite measures over the states when it is read forward. The consumption stage of the portfolio application, from which the listings of these pages are printed, is the running example. The household holds resources m at the arrival perch; the block arvl_to_dcsn writes m_d = m at the decision perch, where consumption c is chosen, and the block dcsn_to_cntn writes savings a = m_d - c. The policy block states the choice by its maximization, the line optimality; the three lines of the endogenous grid method, InvEuler, grid and identification, stand in the methods file beside the stage file, methods.bl, which A builder §2 reads one by one after methodization (Methodization). The block cntn_to_dcsn writes the value V and states its derivative in m_d by a derivative line, D_{m_d}V = 𝑑𝑢(c). The line InvEuler of the methods file reads the derivative of the continuation value in a by the derivative term D_{a}V[>]; neither derivative is a field of a header. The file, as the repository holds it:

    from pathlib import Path

print(Path("applications/portfolio-choice/declaration/stages/cons/cons.bl").read_text(), end="")

    @stage: cons

Xm := ℝ₊₊
Xa := ℝ₊

ρ : [1, inf)

𝑢(c : ℝ₊₊) := c^(1-ρ)/(1-ρ)         :: [id=util]
𝑑𝑢(c : ℝ₊₊) := c^(-ρ)               :: [id=marginal_utility]
Γ(x : ℝ₊₊) := (0, x]

[id=arvl_to_dcsn, (m : Xm, l : ℝ₊) : !arvl -> (m_d : Xm) : !dcsn] {
    m_d = m
}

[id=dcsn_to_cntn, (m_d, c : !ctrl @ ℝ₊₊) : !dcsn -> (a : Xa) : !cntn] {
    a = m_d - c
}

[id=cntn_to_dcsn, (V[>] : [-inf, inf) @ !vlu, c) : !cntn -> (V : [-inf, inf) @ !vlu) : !dcsn] {
    V        = 𝑢(c) + V[>]          :: [id=value]
    D_{m_d}V = 𝑑𝑢(c)                :: [id=marginal]
}

[id=dcsn_to_arvl, (V) : !dcsn -> (V[<] : ℝ @ !vlu) : !arvl] {
    V[<] = V                        :: [id=value]
}

[id=policy, (V[>] : [-inf, inf) @ !vlu) : !cntn -> (c : ℝ₊₊ @ !ctrl) : !dcsn] {
    c      = argmax_{cp : Γ(m_d)}(𝑢(cp) + V[>])   :: [id=optimality]
}

    load_stage(path) reads a stage file into its record, a dictionary that holds the file's text and origin under stage, the calibration and the settings as empty mappings, under methods the list of the additions it read, [] for the stage file alone, and the file's origin and digest under provenance; load_stage(path, [methods_path]) reads the stage file with the methods files its list names, and methods then holds one record with the keys origin and text for each addition, in the order given. elaborate_stage(record) parses the text and constructs the stage. The result is a stage occurrence: the file elaborated once, with its own bindings, sharing no object with any other elaboration of the same file. One file may be elaborated at several positions, in one period or across periods, and each elaboration is a separate stage occurrence, which prints the name the file declares and, when it stands in a trellis, records its position there in its provenance. A stage occurrence is never adjusted in place: it varies only through one of its three bindings or through a different text, which is elaborated again, and a text derived from the file is elaborated as a stage occurrence of its own, with its origin recorded.

    from bellman.stage import elaborate_stage, load_stage

stage = elaborate_stage(load_stage("applications/portfolio-choice/declaration/stages/cons/cons.bl"))
print(repr(stage))

    ElaboratedStage('cons', symbolic)

    The short form names the class, the declared name of the stage and its version. Where the bindings present follow the order calibration, methodization, configuration from its start, the version is one word: symbolic before any binding, then calibrated, methodized and specified as the verbs of The binding verbs are applied in that order. Otherwise the version is the list of the bindings present, in that order: a stage occurrence constructed with its methods files and not yet calibrated prints methods, and methods, settings once it is configured.

    A record may also hold, as mappings, the sources of the calibration and the settings, and under methods the additions load_stage read, which are read with the stage text when the stage is constructed and bound by no verb: elaborate_stage(record) constructs the stage from the stage file with its additions and binds each source the record supplies, in the order of The binding verbs §1, a non-empty calibration as calibrate binds it and a non-empty settings as configure binds it. Under methods anything but that list is refused under record-shape, the mapping {"methods": []} among it, and the refusal says to write methods: []; an empty mapping is admitted as the empty source of a record written by hand. An empty source binds nothing, so the record load_stage(path) returns gives the symbolic stage, as above, and elaborate_stage(record, bind=False) gives the symbolic stage whatever the record holds, the additions left out with the other sources. The stage is constructed, the bindings are made on it, and it is copied once, at the end; for a record without additions the result equals, provenance included, the stage the two verbs bind one after another on elaborate_stage(record, bind=False) with the record's own mappings, each binding that stage itself. A source is refused as its verb refuses it.

    record = load_stage("applications/portfolio-choice/declaration/stages/cons/cons.bl")
record["calibration"] = {"ρ": 6.0}
calibrated = elaborate_stage(record)
print(repr(calibrated), calibrated.par.ρ)
print(repr(elaborate_stage(record, bind=False)))

    ElaboratedStage('cons', calibrated) 6.0
ElaboratedStage('cons', symbolic)

    Two further functions of bellman.stage construct the same kind of object. elaborate_text(text, origin) elaborates a text held in memory and records origin as its source. make_stage(term, spans) constructs a stage from a syntax tree that parse_with_spans, of bellman.syntax.lower, has already read, where spans holds the source positions that a refusal cites, or is None for a tree without positions; calling the two separately distinguishes a parsing error from a construction error.

    from pathlib import Path

from bellman.stage import elaborate_text, make_stage
from bellman.syntax.lower import parse_with_spans

text = Path("applications/portfolio-choice/declaration/stages/cons/cons.bl").read_text(encoding="utf-8")
print(repr(elaborate_text(text, "applications/portfolio-choice/declaration/stages/cons/cons.bl")))
term, spans = parse_with_spans(text, filename="cons.bl")
print(repr(make_stage(term, spans)))

    ElaboratedStage('cons', symbolic)
ElaboratedStage('cons', symbolic)

    A stage keeps no syntax tree: the tree is discarded once the stage is constructed, and every later answer is read from the stage. A file that construction cannot read is refused with a ConstructionError, which names the file position, the rule the file does not satisfy and what to write instead; a form of the language that no construction rule reads is refused with NotConstructed, a kind of ConstructionError. Both are exported by bellman.refusals, and Refusals gives an example of every rule.

    2 The seven attributes¶

    A stage is a frozen record, a Python object whose attributes cannot be reassigned once it is built, with seven attributes and no others. definitions, initial and _builders state the model, the third under a private name: it is the stored record of the two builders graphs, which a reader reaches through stage.builder (The builders graphs §1); bindings holds the three bindings of this version; provenance records the file, its digest and where each binding was read from.

    import dataclasses

print([field.name for field in dataclasses.fields(stage)])
print(stage.bindings)
print(stage.provenance)

    Attribute Python type What it holds
    name str the name the stage declares
    metadata read-only mapping the file's @ lines other than @stage
    definitions read-only mapping from an identity to a Definition every declared name once, and one record for each line of a block
    initial record of two graphs the graphs on fields, backward and forward
    _builders record of two graphs the graphs on functions and measures, backward and forward, which stage.builder reads by the pair of perches each builder joins
    bindings record of three mappings the calibration and the settings of this version, each None until bound, and blocks, the rows a solution method's lines add at the operative level, by the builder each opens; the methods of a version are no binding but the components of its signatures, read from the typing entries of the definitions table (Methods and places)
    provenance read-only mapping the file's path, text and digest, under versions the version of the package and the digests of its grammar files, and under sources where each binding was read from and its digest; on a bound version, the verb that made it, its source and, under parent, the provenance of the version it was made from; for a stage occurrence in a trellis, also its position there

    Nothing else is stored. Whatever the definitions, the graphs and the bindings determine is computed when it is asked for, and the answer is then kept on the version it was asked of. calibrate and configure keep the answers the stage had computed from the definitions and the graphs alone, which neither changes, and discard those that read a binding, which the stage computes again when they are asked for; methodize elaborates the stage anew from the union of the stage file with its methods file, whose entries and lines enter the definitions table and whose solution method's lines change the operative builders, and keeps only the answers of the stage file's own construction and of the initial diagrams (The binding verbs §1). Of the three bindings, the calibration completes the economic problem, and the methods and the settings record how it is to be computed, changing no assertion of the model.

    print(stage.name, len(stage.definitions))
print(sorted(stage.provenance))

    cons 17
['origin', 'sha256', 'sources', 'text', 'versions']

    The attributes that hold the model, the mapping of the builders and the three tables read from the model answer objects of their own, each of which has a page; the three perches answer objects too, which have a section, The builders graphs §2:

    for name in ("definitions", "initial", "builder", "arvl", "dcsn", "cntn", "par", "settings", "methods"):

    stage.definitions is the definitions table; stage.initial holds the initial diagrams; stage.builder reaches each builder by the pair of perches it joins; of the three perches, stage.arvl and stage.dcsn each reach the builders of the edge that leaves the perch, the step from that perch to the next, and stage.cntn, which no edge of the stage leaves, refuses both directions with the reason (The builders graphs §§1 and 2); stage.par and stage.settings are the parameters and the settings; and stage.methods holds the bound methods. No attribute can be assigned after construction, and no answer changes the stage: a version with other bindings is a new object.

    3 The printed view¶

    stage.view() answers the stage's printed view, a text the package writes each time it is asked and stores nowhere; print(stage) prints the same text. It lists the perches with their fields, the fields by role, the blocks with the fields they read and write, the definitions by kind, the four graphs, the bindings and the directions of the two initial diagrams. Its block signatures come from the file, the inputs, the outputs and the perches of each block as its header declares them; the rest are the package's own summaries, such as the count of definitions by kind.

    The view is a sheet, the printed form every view of the package takes. Its first line is the sheet's address, BELLMAN-SYM / STAGE cons, with the version at the right margin; the second says what the object is, one stage occurrence of the file it was elaborated from; a heavy line closes the title. Each section opens with its label in capitals and a hairline to column 78, and no line of the sheet is wider. The printed record of a piece below the stage, its card, has the same width and a title over a heavy line, and opens each of its sections with a heading at the left margin instead (A piece §1).

    Section What it prints
    PERCHES the fields of each perch with their roles, the marks ≺ ∼ ≻ standing for arrival, decision and continuation
    FIELDS the same fields by role, the states, the controls, the values and the shocks each on one line
    BLOCKS the blocks in file order, each with the arrow of its direction, its inputs, the coordinate it is read at and its outputs; a control a block names among its inputs is that coordinate and no wire, so it stands after at (The initial diagrams §3)
    DEFINITIONS the records by kind, with the count of each kind and the records in file order, the laws of motion and the value aggregators by their rules, so that the table says what the model is (The definitions table)
    GRAPHS the two initial diagrams as present or refused, and each builders graph's mapping, its inputs to its outputs, so that the sheet says what each graph maps and where each is asked for (The builders graphs)
    BINDINGS the three bindings, the section's hairline drawn in dashes while one is missing, each missing binding naming the verb that supplies it (The binding verbs)
    DIRECTIONS one line for each chain of blocks, the wires of each block grouped by perch on either side of the direction's arrow, the policy block on its own line; the card of each initial diagram prints the lines of its own direction under Source

    4 What the stage contains¶

    stage.list() names the pieces the stage contains directly: the blocks of the two initial diagrams under initial, each with its kind and direction, and the builders of the two builders graphs under builder, each by the id of its block with the pair of perches it joins, or policy for the policy builder, and the word of its direction, the listing that stage.builder.list() answers.

    print(stage.list())

    initial
  cntn_to_dcsn   block, backward
  dcsn_to_arvl   block, backward
  policy         block, backward
  arvl_to_dcsn   block, forward
  dcsn_to_cntn   block, forward
builder
  arvl_to_dcsn   arvl → dcsn, fwd
  dcsn_to_cntn   dcsn → cntn, fwd
  cntn_to_dcsn   cntn → dcsn, bwd
  dcsn_to_arvl   dcsn → arvl, bwd
  policy         policy, bwd

    stage.denote() answers the stage's two operators, the backward builders graph on value functions and the forward builders graph on measures, under the words backward and forward: the same two records that stage.builder.bwd.denote() and stage.builder.fwd.denote() answer on The builders graphs §3. The stage answers no signature(), since it is two operators and not one, and its sheet holds no card. Its record prints the two graphs' inputs and outputs and their builders in order, the line the policy is declared by, the conditions, the lines of the file, and at its foot the file, the perch marks the file writes and the appendix whose rules read it:

    stage.obligations() answers every condition the construction states, each under its name, with its formula or, where it has none, its sentence, and its status: [established] marks a condition that the declarations or the calibration settle, and a condition without the mark remains to be checked. A condition is required where no declaration settles it, which does not make it hold; assumed where the construction states it without deciding it; and established where the declarations or the calibration settle it, the declaration or the values it was decided on being its evidence. A status other than required is printed in brackets, and a part the package cannot derive is marked unresolved and never silently replaced. stage.diagnostics() answers nine questions about the completeness of the stage, in this order: complete_signature, whether every declared output is constructed; missing_builders, the blocks with no builder; exposed_inputs, the fields no block supplies; unused_outputs, the outputs nothing reads; forward_map, the lines that read a field of a later perch through a transition the stage does not write; builder_choice, the pairs of perches that several builders could serve; external_calls, the functions the lines call that no definition of the stage declares; unread_inputs, the value fields a backward block's header lists and no line of the block reads, each recorded as a diagnostic that names the block and the field and left out of the block's builder; and ready_for_interpretation, whether the stage is ready to be interpreted.

    The package holds one schema, bellman/display/stage-encoding-2.6.schema.json, whose identifier ends in /stage-encoding/2.6; it describes the whole document, and the package's tests validate the document of every application stage against it. Under derived stand the answers the denotations give, each node with a kind spelled <namespace>.<Kind>, such as records.Wire or terms.Sym, in one of the five namespaces the schema lists, terms, semantic, records, predicates and methods.     The entry of a set marked !categories (Symbol conventions §9.2) holds one key more, categories, with the identifier written after the marker, or null, and the pairs of a code and its category's name in increasing code order, {"identifier": "household_status", "codes": [ [0, "newborn"], [1, "old"] ]}; no other entry holds the key, which the schema admits as optional.     A value an author writes, in a binding, in a method's settings or in the provenance, is encoded with one reserved key, so that json.dumps(stage.encoding(), allow_nan=False) also accepts the answer. A floating-point positive infinity is written {"$bellman": ["float", "inf"]}, and negative infinity and NaN "-inf" and "nan" in the same form, while the strings "inf", "-inf" and "nan" stay strings. An authored mapping that holds the key $bellman is written {"$bellman": ["mapping", …]}, with the list of its entries in their order, each a pair of the key and its encoded value, so that it is never read as a float. The rule applies to such values alone: the fixed fields of the graphs, the definitions and the methods are written as they are, and no admissible number is added or removed.

    Within Python a version, and so a trellis of versions, is written and read back by the standard pickle, the form in which multiprocessing and mpi4py send an object from one process to another: what is read back equals what was written, and computes its answers again when they are asked for. Importing the module bellman.native.hypergraphs, which nearly every public name of the package imports (load_stage, load_trellis, the error classes and a bare import bellman do not) and which reading such a pickle imports, registers with the standard module copyreg a rule for types.MappingProxyType that holds in the whole Python process: pickle and copy.deepcopy, which otherwise refuse a read-only mapping, then accept any read-only mapping in that process and write it as a new read-only mapping over a copy of its entries.

    From a shell, python -m bellman applications/portfolio-choice/declaration/stages/cons/cons.bl prints the printed view of §3; --encoding prints the encoding, --dossier the printed answers of the stage with its source, and --refusals the catalogue of refusals. A command that succeeds exits with status zero; a refused stage exits with status one and its explanation.

    5.1 Supplied continuation fields¶

    stage.check_inputs(values) checks the fields received at the continuation perch. The mapping names every external input exactly as its owning backward header writes it: V[>] keeps its mark, while a kept name such as L stays bare. Fields produced inside the stage are excluded. Selecting a method does not change these declared requirements.

    A field typed !cnst receives its whole value. A scalar or finite table is checked against its declared set, using calibrated parameters and supplied constants where its bounds read them. For example:

    from bellman.stage import elaborate_text

bound = elaborate_text("""@stage: bound
[id=cntn_to_dcsn, (L : (-inf, 0] @ !vlu @ !cnst) : !cntn
    -> (B : ℝ @ !vlu @ !cnst) : !dcsn] {
    B = L
}
""", "bound.bl")
assert bound.check_inputs({"L": -2}) == ()

    Supplying L = 2 raises ConstructionError, naming L and its declared set. Missing and unknown names also raise ConstructionError. These failures use the rule continuation-input. The check preserves the supplied mapping, arrays and other values.

    An ordinary value field receives a function of its declared state coordinates. For the consumption stage used above:

    conditions = stage.check_inputs({"V[>]": lambda a: 0.0})
for condition in conditions:
    print(condition)

    The returned conditions remain required: the checker does not evaluate the function or prove its domain, range, dependence or measurability. A fixed callable supplied as the whole value of a function-valued constant likewise leaves membership unresolved. An empty tuple means that the supplied representation decided all input checks; it proves nothing about the stage's other conditions.

    stage.obligations() lists the input requirements before data are supplied. Checking data does not change that list or any binding. Numerical callers retain the returned conditions and pass the same mapping to a builder's kernels(inputs=values) before constructing grids or numerical operators.

    6 What each check establishes¶

    Check What it establishes Where it is reported
    Parsing The file is written in the grammar of the language. A ConstructionError under the rule syntax, with the line and a mark under the column.
    Construction The declarations, the block headers and the equations satisfy the rules by which a stage is constructed. A ConstructionError that names the rule and the item of the file.
    The analytic conditions That the declared sets contain the values and that each expectation is finite; the stage states no condition on whether a maximum is attained. stage.obligations(), each condition required or established; construction establishes none that the declarations do not settle.
    The numerical checks That a chosen routine approximates the solution adequately. Outside the package, with the routine.

    Success at one level establishes none of the levels below it: a stage that is constructed has solved no household problem.
