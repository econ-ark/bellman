    Stages¶

    Summary

    Write a household's consumption problem in a .bl file. Declare what the household knows, what it chooses, and which equations determine resources, savings, and value. The example includes income risk and a borrowing constraint. Further examples declare indexed city data and integer states with recorded category meanings.

    Relationship with other documents

    Builds on — The stage: the stage, its perches and its fields in prose, on a buffer-stock model like this page's. Used by — Field equations: consumption as a separate stage file and its first-order equations; Periods: joining stages. Formal account — Appendix C: conditions for interpreting fields as functions of states.

    1 Stages and perches¶

    A household begins with nonnegative assets b, earns the gross return R, and observes positive income y. It chooses consumption c from resources w = R*b + y and retains savings a = w-c. Consumption must be strictly positive and savings nonnegative, so the feasible choices satisfy \(0<c\leq w\).

    A stage is a module of a Bellman problem with three information sets, called perches. In this example they distinguish income arriving, consumption being chosen, and savings being available for continuation:

    Perch What the household knows State used in this example
    Arrival Beginning assets, before the current income draw. b, beginning assets.
    Decision Beginning assets and realized income; consumption is chosen here. w, resources available to consume or save.
    Continuation The consumption choice and the resulting savings. a, savings available for the future.

    A state summarizes the information needed for the remaining problem. We assume resources suffice for the consumption decision and savings suffice for continuation value. The household may remember more than these scalar states record; the perch describes its information, whereas the state supplies the arguments of its value function. These sufficiency assumptions are part of the economic model, not consequences of the notation.

    2 Declarations and types¶

    A declaration is a name, a colon and a type. The type says what the name may denote: a set of admissible values, called its domain, a role in the decision problem, an information set, or a combination of these. The complete file in §4 declares a parameter, a shock, a control and a value this way:

    β : (0,1)
y : ℝ₊₊
c : ℝ₊₊ @ !ctrl
V : ℝ @ !vlu

    A type is a list of components joined by @. A component is either a set, written in mathematical notation, or a word with the prefix !. The components are unordered, so c : ℝ₊₊ @ !ctrl and c : !ctrl @ ℝ₊₊ declare the same type. A type contains at most one role word and one perch word; it may contain several sets, and the declared name then lies in each of them, as in β : (0,1) @ (0, R^(ρ-1)) (Symbols and conventions §9.2). The join @ combines descriptions of one quantity; it never multiplies sets. A quantity valued in a product is declared with × inside its set, as x : ℝ × ℝ. The prefix is what marks a vocabulary word, so a bare word is always a name and no word is reserved.

    Word What it says
    !arvl, !dcsn, !cntn The name belongs to the arrival, the decision or the continuation perch.
    !ctrl The name is a control, chosen at decision.
    !vlu The name is a value.
    !shck The name is a shock; written when the shock is declared before its law.
    !state The name is a state; a restatement, since a name with a set and a perch and no role word is a state.
    !node Written in a statement's annotation, not after a colon: the statement is a separately inspectable computation (Appendix D).

    Parameters carry a set and neither a role nor a perch, as R : ℝ₊₊. States are declared with a set alone; their role is derived. A value carries its role word !vlu, and the control carries !ctrl. A marginal value is no field and has no role word: the derivative of a value is read where a line needs it, by the term D_{a}V[>], the derivative of the continuation value in the continuation coordinate a (Field equations §2).

    A field name is local to the stage occurrence that declares it. Another stage may use the same spelling for a different field, and a matching name does not by itself connect the stages. All branches of one stage share its declarations, so separate branch states need separate names. A parameter has different scope: a name declared by two stages in one period denotes one period parameter, with one compatible declaration and one value; the same name in another period denotes another parameter. Fields and Parameters give these distinctions.

    The colon binds to the smallest complete object on its left. In (w, c : ℝ₊₊ @ !ctrl) the type belongs to c alone, and w is a reference to an earlier declaration. Parentheses make several names one object: (w, c) : S declares two names jointly constrained by the set S, and tuples nest wherever a name may stand, as in ((k, h) : K, y) : !arvl. A tuple of two names and one name valued in a product are different declarations: (w, c) : ℝ × ℝ constrains two names jointly, whereas x : ℝ × ℝ declares one name whose components are selected as x[1] and x[2] (Equation parsing rules).

    A law is not a type. A shock's distribution is an object, like the number 0.96, and two shocks with the same distribution are not interchangeable, so the distribution is assigned on its own line with ~, after the shock's set has been declared:

    y : ℝ₊₊
y ~ LogNormal(μ_y, σ_y)

    The fused form y : ℝ₊₊ ~ LogNormal(…) is not admitted. The distribution declaration makes y a shock; use !shck to declare it before supplying its distribution. A joint distribution takes a tuple subject, (Ψ, θ) ~ N(…). Separate declarations imply conditional independence given the source coordinates unless one names the other as an argument. The stage records this factorization as an assumption. Shock distributions lists the families a shock's distribution may take, LogNormal among them.

    Block signatures are typed the same way. In [id=arvl_to_dcsn, (b : ℝ₊, y) : !arvl -> (w : ℝ₊₊) : !dcsn], the word after each parenthesized side names the perch of every coordinate listed on that side, with two exceptions: a shock listed on a side is an argument of the block's equations and belongs to no perch, and a control is at decision wherever it is listed. A backward block's header lists the value fields it reads and writes and the controls at which its lines are read, and no state: a state of the perch at which the block's output stands is a coordinate of that output, which a line reads without listing it, and a listed state is refused under header-coordinate. It lists no marginal value either: a line reads the derivative of a value the header lists by the term D_{a}V[>], and a line of a value builder's block may state the derivative of the value the block writes, D_{m_d}V = 𝑑𝑢(c), with nothing listed for it (Field equations §2). A value field the header lists and no line of the block reads is admitted: it is left out of the block's builder, and the elaboration records it as a diagnostic, the header lists V[>], which no line of the block reads, in place of a refusal. A name's set is declared at its first occurrence, in the preamble or on a side, and its perch is fixed the first time it appears on a perch-named side, by a perch word in its own type, or by its perch mark. A later occurrence may restate the set or the perch, and the restatement must agree with the declaration; it may not change it. A side may omit its perch word only when the perch of every non-shock coordinate on it is already known, as the portfolio application's policy signature (V[>]) -> ς does; a perch is never guessed. Perch tagging rules gives the information-set reading of these rules.

    Definitions and binders use the same colon. A named set is defined with :=, as Xa := ℝ₊ or Xa := [0, ā]. A function is defined with typed arguments, 𝑢(c : ℝ₊₊) := c^(1-ρ)/(1-ρ), whose c is local to the definition and is not the stage's control. A definition without arguments whose right side is arithmetic in the parameters, h := 1/(1 - Γ/R), defines a derived parameter: calibration computes its value from the definition and refuses a value supplied for it (Parameters). Similarly, the binder of a maximization ranges over a feasible set written after a colon, argmax_{c : Γ(w)}(…), with the bare binder argmax_{c} when the control's declared set is its feasible set (Constraints).

    These sets describe admissible economic values. A numerical grid used to approximate a continuous domain is written separately, in the methods file (Methodization §3.2).

    The complete file uses the following spellings:

    Spelling What the modeller states
    R : ℝ₊₊ The gross return is a strictly positive parameter.
    c : ℝ₊₊ @ !ctrl Consumption is a strictly positive decision control.
    V : ℝ @ !vlu V is a real-valued value field.
    𝑢(c : ℝ₊₊) := c^(1-ρ)/(1-ρ) Utility is a function of positive consumption.
    a = w - c Savings equal resources less consumption.
    y ~ LogNormal(μ_y, σ_y) The separately declared income shock has the specified law.
    :: [id=savings] The equation has the address savings within its block.

    Thus : declares a type, @ joins its components, := defines, = states an equation, ~ supplies a shock distribution, and -> separates the two sides of a block signature. @ appears in exactly one other place, the metadata line @stage: buffer_stock that names the stage.

    The file declares the discount factor β between zero and one and risk aversion ρ greater than one. For example, ρ = 2 gives utility \(u(c)=-1/c\), finite on positive consumption. This example excludes unit risk aversion, where the displayed formula would divide by zero. The income convention is explicit: conditional on arrival information, log income is normal with mean μ_y and standard deviation σ_y. This conditional distribution is constant given that information, so current income is independent of earlier observations. Positive income ensures positive resources even at zero beginning assets. A zero standard deviation gives deterministic positive income.

    2.1 Indexed data¶

    For a household choosing among J cities, the number of cities can remain a parameter when the stage is written. Declare the city set and the data indexed by it:

    J : ℤ @ [1, inf)
L_J := {1, …, J}
δ : L_J → ℝ
dist : L_J × L_J → ℝ₊

    The collection δ supplies one payoff per city, and dist supplies one distance per ordered pair of cities. If the current city is declared as a state i : L_J and the destination as a control j : L_J @ !ctrl, an equation reads their entries as δ[j] and dist[j][i]. Their use as indices does not determine their economic roles: i records the current location, j is chosen, and J determines the size of the common domain.

    Every destination leads to the same successor stage, so the choice is one block and not a branching stage: [id=dcsn_to_cntn, (i_d, j : !ctrl @ L_J) : !dcsn -> (i_n : L_J) : !cntn] { i_n = j } retains the chosen city as the integer continuation state, and the number of cities stays the parameter J.

    A numerical key must be integer-valued, including when a parameter determines it. A listed set such as S_θ := {0, θ} ⊂ ℤ is also admitted, with an integer-valued parameter θ; its keys need not be consecutive. By contrast, entries such as payoffs, distances and wages may be real-valued. In q[s] with s : S_θ, the value of s identifies a key; it is not a position in the list supplied at calibration. Positions counted from one select components of a fixed tuple, as in x[1] and x[2] for x : ℝ × ℝ.

    Calibration supplies the values of J, δ and dist, checking the integer bounds and the number and domains of their entries. A different J uses the same stage declaration with correspondingly sized data. Symbol conventions §9.2.1 gives the admitted index sets, data order and a calibration example. Each index's declared domain must fit the corresponding table domain: a state ranging over cities and an outside option cannot directly select from a table defined only on cities (Appendix D §5.2).

    2.2 Category codes¶

    A household's status can be an integer state whose codes have recorded meanings. Define the set and give each member a category name:

    HouseholdStatus := {i : ℤ | i >= 0, i <= 1} :: [!categories household_status, newborn=0, old=1]
n : HouseholdStatus

    The expression between braces is a comprehension: it contains the integers satisfying every condition after |, with i local to that definition. The annotation assigns the name newborn to 0 and old to 1. A state declared on HouseholdStatus therefore takes integer values, while the stage retains the correspondence between those values and their meanings. Recording categories does not create a branching stage; the blocks still specify the state transitions and any choices.

    Equations use the codes. For example, a transition to old age is written n_next = 1, with n_next also declared on HouseholdStatus; writing n_next = old is refused because the annotation does not declare old as a name usable in equations. Ordinary arithmetic remains available, so 100 - 120*n equals 100 for a newborn household and −20 for an old one. With three or more categories, using an affine formula in the code imposes equal steps in that formula; assigning codes alone supplies no distance between categories.

    The marked set must have a nonempty integer range bounded by literal inequalities, with exactly one name per code and one code per name. Use the shared identifier household_status when these meanings are used across stage files; Periods §2 explains how connections check them. The complete annotation rules and the distinction from collection index sets are in Symbol conventions §9.2.2.

    3 Builder blocks¶

    A field is a quantity interpreted in its declared information set. A block groups equations between declared inputs and outputs. These two blocks, taken from the complete file in §4, express the household's budget:

    [id=arvl_to_dcsn, (b : ℝ₊, y) : !arvl -> (w : ℝ₊₊) : !dcsn] {
    w = R*b + y                  :: [id=resources]
}
[id=dcsn_to_cntn, (w, c : ℝ₊₊ @ !ctrl) : !dcsn -> (a : ℝ₊) : !cntn] {
    a = w - c                    :: [id=savings]
}

    Read the first signature from left to right: beginning assets and the income shock determine decision resources. Here ℝ₊ means nonnegative real numbers and ℝ₊₊ means strictly positive real numbers. Income and the return parameter are declared elsewhere in the same file. The second signature declares c as a control, a quantity the household chooses at decision, and a as nonnegative continuation savings. Its equation and domains jointly impose the borrowing constraint; the maximization in §4 ranges over these feasible choices.

    The words !arvl, !dcsn, and !cntn identify the three information sets, the perches. A shock listed on a signature side is an argument of the transition: listing y on the arrival side does not say that income has already been observed. Similarly, a control retains its decision role when a later block lists it with continuation inputs. Perch tagging rules explains both exceptions.

    The identifiers arvl_to_dcsn, resources, and savings supply addresses for inspection and supported numerical methods. Their names do not supply mathematical equations. Renaming resources consistently changes its address but preserves w = R*b + y.

    4 A complete stage file¶

    Save this source as buffer_stock.bl. The final three blocks add current utility to continuation value, average over income before it is observed, and choose a feasible consumption maximizer:

    @stage: buffer_stock

β : (0,1)
ρ : (1, inf)
R : ℝ₊₊
μ_y : ℝ
σ_y : ℝ₊
y : ℝ₊₊
y ~ LogNormal(μ_y, σ_y)

𝑢(c : ℝ₊₊) := c^(1-ρ)/(1-ρ)

[id=arvl_to_dcsn, (b : ℝ₊, y) : !arvl -> (w : ℝ₊₊) : !dcsn] {
    w = R*b + y                  :: [id=resources]
}
[id=dcsn_to_cntn, (w, c : ℝ₊₊ @ !ctrl) : !dcsn -> (a : ℝ₊) : !cntn] {
    a = w - c                    :: [id=savings]
}
[id=cntn_to_dcsn, (V[>] : ℝ @ !vlu, c) : !cntn -> (V : ℝ @ !vlu) : !dcsn] {
    V = 𝑢(c) + β*V[>]            :: [id=value]
}
[id=dcsn_to_arvl, (V) : !dcsn -> (V[<] : ℝ @ !vlu) : !arvl] {
    V[<] = E_{y}(V)              :: [id=value]
}
[id=policy, (V[>]) : !cntn -> (c) : !dcsn] {
    c = argmax_{c}(𝑢(c) + β*V[>]) :: [id=choice]
}

    Here V[>] is the continuation-value input, V is decision value, and V[<] is arrival value. [<] and [>] select the stage's information sets; they do not mean the preceding and following calendar periods. A bare field or [~] uses the decision interpretation when its declaration and equation context establish it, as for V here. An ordinary collection selection such as q[a] has a different meaning from evaluating a function at q(a); see Equation parsing rules.

    The continuation input is a function \(W:[0,\infty)\to\mathbb R\) of savings, supplied by the next period or a terminal boundary. For a given feasible consumption choice, the value equation represents

    \[ Q(w,c)=u(c)+\beta W(w-c). \]

    The policy block chooses \(\pi(w)\in\arg\max_{0<c\leq w}Q(w,c)\), and decision value is \(v(w)=Q(w,\pi(w))\). Before income is observed, arrival value is \(B(b)=\int v(Rb+y)\,\nu_y(dy)\), where \(\nu_y\) is the specified income distribution. The expectation therefore uses the policy selected after income is observed. Setting \(W=B\) would be an additional stationary-model condition; the stage does not impose it.

    Assume \(W\) is finite and continuous on every compact savings interval and select a measurable maximizer. The maximum is attained because utility tends to minus infinity at zero consumption while continuation value is bounded on the feasible savings interval. Concavity of \(W\) makes the consumption maximizer unique. The arrival equation additionally requires \(\int|v(Rb+y)|\,\nu_y(dy)<\infty\); bounded continuous \(W\) is a sufficient case under this lognormal distribution. Appendix C R5–R8 gives the state-representation, integration, and policy conditions.

    This documentation example modifies the repository's applications/consumption-savings-iid/declaration/stages/cons_savings_iid/cons_savings_iid.bl: it uses wholly positive income, restricts utility and discount parameters, and states the choice by the maximization alone, as that application's stage file also does, over its declared feasible set Γ(w) = (0, w]; the application writes the candidate lines of the endogenous grid method and the derivative lines of its values in its methods file, methods.bl beside the stage file (Methodization). The displayed source is the example taught here; it does not certify the different application source.

    5 Files and next steps¶

    The stage file states the model equations. To solve a finite-horizon problem, supply continuation and terminal values, methods, settings, and calibration. The methods file is written in the same language, beside the stage file; the settings and calibration files are YAML. Field equations separates consumption from income and discounting so that these stage files can be joined in a period.

    A block is the authored typed group of equations between declared inputs and outputs, and a builder is the operator that block defines: a transition, a value calculation, or a policy relation. The builder keeps the block's id as its name, and a reader reaches it in the elaborated stage by the pair of perches its block joins, stage.builder["cntn", "dcsn"] for the block cntn_to_dcsn, the policy builder by its own key, stage.builder["policy"], or from a perch, which reaches the builders of the edge that leaves it, the step from that perch to the next: stage.dcsn.builder.bwd is the same builder, which constructs the value at the decision perch, stage.arvl.builder.bwd the builder of dcsn_to_arvl, and stage.dcsn.builder.policy that of policy. The backward builders used in solution form the graph stage.builder.bwd, and the forward ones used in simulation the graph stage.builder.fwd (The builders graphs §§1 to 3). To make one equation separately inspectable, add !node to its annotation; Field equations demonstrates this with savings. Neither a block's name nor a numerical-method choice supplies a missing equation.

    For loading, use the factory API, and for inspection the API. The stage retains interpreted equations and definitions in a graph of mathematical operations and their typed connections. With the required assumptions, its field equations can also be inspected as functions of states. Their mathematical relationship is described in Appendix C.

    Technical details

    .bl inherits its syntax from dynspec, an expression language. Parsing constructs a temporary abstract syntax tree, a structured representation of the written file. Checked interpretation constructs the stage's semgraph, the semantic graph of its equations, and discards that tree and its source spans.

    Abstract grammar: FILE

    This is a projection of the dynspec host grammar in ASDL, the notation for syntax-tree constructors. * means an ordered list and ? means optional. The omitted declaration alternative and the definitions of the referenced sorts belong to the full grammar; this projection does not redefine them.

    file = FILE(item* items)
item = Metadata(identifier key, scalar value)
     | Statement(stmt core, annotation? annot)
     | Block(annotation tag, item* body)

    Keys. items preserves source order; key and value give metadata; core is a statement with optional annot; tag is a block header and body its contents. These are ASDL fields, not YAML keys to write in a .bl file. scalar, stmt, and annotation are host sorts.

    Head. Stage metadata identifies the stage file; the syntax-tree root remains FILE.

    Denotes. Interpretation constructs the declared stage equations and their typed connections, subject to Appendix C.

    Status. The three item constructors shown retain their argument order and multiplicity. Scope, type agreement, and complete output definitions are construction checks, not consequences of this grammar box.
